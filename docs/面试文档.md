## 一、一分钟口述

> Assay 是一个解决 Agent 版本迭代「改完能不能发、退化在哪」的评测准出平台。
>
> 1. **准出与诊断**：四层评测（结构/行为/一致性/反馈），默认把大模型挡在硬门禁之外保证决策可复现——自由文本 LLM 复核只给语义线索和修改建议，不进判定；可选的 G-Eval 指标能按 hard/soft 配置参与门禁，但模型失败记为 ERROR、可缓存并受预算约束；决策输出带全量条件和证据路径，能审计；版本退化时不重跑 Agent，直接拿两次已落盘的轨迹对齐，定位第一个出现分歧的步骤，并把同类失败按角色、差异类别、模块、动作归并成簇。
> 2. **异构接入**：设计统一适配契约，HTTP、Java、离线导出文件、AgentScope 都能归一化成同一套**可比较的**轨迹模型——统一的是最小完整集和步骤签名序列，框架自带的业务字段留在扩展字段里，不承诺跨框架语义一致；差异全部挡在适配层，核心只认统一模型。
> 3. **异步调度**：平台定位是轻量、能嵌进 CI，一个 jar 就能跑，所以自研了文件/JDBC 双存储的队列；用租约、心跳、幂等保证可靠性，人工复核的结论再归档回去，成为下一轮评测的数据。

## 二、三个 Bullet 的追问防守

### 1. 发布准出与首错定位

**这个项目解决的真实痛点是什么？** 没有它的时候，Agent 改完只能靠人看几条输出、凭感觉判断能不能发；退化是事故驱动的——线上出问题才回头找是哪一步变的。它把「感觉」换成「可复现的对比 + 可审计的决策」。

**准出的是哪个版本？** 是组合版本：模型、Prompt、工具配置、编排逻辑任一项变化都算一次候选，评测针对的是这套组合跑出来的轨迹，而不是单个文件。

**为什么按四层分，而不是「正确性/相关性/安全性」？** 因为我的分类依据是**确定性**，不是业务维度。结构和行为能客观计数，可以做成硬门禁；一致性和反馈带主观和随机性，默认只做告警和复核。这个划分直接决定了哪一层能拦发布。

**四层分别看什么？** 结构看轨迹完整性和必填字段；行为看步数、延迟、工具序列、重复步骤、权限拒绝；一致性看多次运行和跨版本的差异；反馈看人工结论和语义建议。

**一致性和反馈不拦发布，那四层是不是名不副实？** 这是策略选择，不是能力限制。每个检查项自带严重级别（直接拦 / 告警 / 只记录），重要的一致性规则完全可以配成硬门禁。默认不让它拦的原因很实际：不稳定本身多半是模型随机性，一拦就会把「这个版本不稳定」和「这个版本变差了」混为一谈，前者该转人工，后者才该回滚。所以四层不是四票加权，而是**两层硬门禁 + 两层准入资格**。但「准入资格」这句话要说准、别说大：它目前真实的落点只有两个——**配了质量门禁时，样本量不足会直接进回滚**（`minimum_samples` 是质量门禁的一个阈值，不是一致性告警；默认策略里质量门禁是空的，所以这一条要显式配才生效）；**关键一致性规则配成硬门禁级别时才会真拦**，而且它拦在 **rollback** 通道上，不是 reject——因为规则一旦配成 hard，这条用例就是硬失败，硬失败进的是回滚判定。默认状态下，一致性告警并不会阻止自动准出，它只是把可疑用例推进人工复核队列。这个差别自己先讲出来，比被追问「那告警了 CI 拿什么码」强。

**LLM 为什么不能进硬门禁？** 有随机性、成本、延迟，还可能被注入；同一份输入跑两次结论不同，门禁就形同虚设。**「隔离」这两个字要主动解释，不能等对方带着「是不是吹的」来问**：隔离的是判定链路，不是把非确定性消除掉——LLM 仍然会波动，只是波动落在反馈层，不参与硬通过率和软告警计数。它在系统里的落点很窄：只在这一条用例**已经被规则判为可疑之后**才被调用，结果写进这条用例的 `llm_review` 字段，跟着复核队列一起落盘，报告里标「机器建议、未经人工确认」。所以它连「提档」都没有独立通路——进不进复核队列由规则决定，不由它决定；它更不能把硬失败改成通过。**这里有个缺口要认**：模型输出只做宽松 JSON 解析，解析失败记一个 `parse_error`，没有严格 schema 校验，字段缺失要靠下游容错。

**2026-11 补一句，避免绝对化**：上面说的是默认的 `llm_review`。如果显式配置 `geval` 指标，模型分数可以按 hard/soft 参与门禁；区别是它有固定评分步骤、0-10 / strict 0-1 校验、缓存和预算，失败落 `ERROR`、`skip/error` 不计入通过率。所以准确说法是「默认复核非权威，语义评分是 opt-in 的可门禁指标」，不是「LLM 永远不进判定」。

**缺失指标怎么办？** 留空，不补零。补零会把「没测到」伪装成「表现好」；同时记录覆盖率，关键目标覆盖不足就直接拦，不给自信的结论。

**同一版本跑两次，准出结论会不会变？** 要分两层说，不能一句「不会」糊过去。**判定本身是纯函数**：给定同一份归一化轨迹和同一份配置，结论唯一、可重放，链路里没有随机数、没有模型调用；归一化也是确定的——字段映射、忽略列表、截断上限都是配置，不打乱顺序、不引入环境依赖。**但两次运行给的不是同一份轨迹**：延迟、步数、模型输出都可能变，所以对真实 Agent 来说，判定逻辑确定不等于结论必然相同。确定性适配器（echo、本地参考 Agent）下两跑结论一致；真实 Agent 要靠一致性层和多次运行暴露波动。结构层只查轨迹标识非空、最终输出非空这类与时间无关的条件，不会因为「这次跑得慢」而变；会变的是行为层里的延迟类阈值，那测的是 Agent，不是判定。

**三个集合怎么分工？** improvement 证明改好了，regression 防弄坏老功能，holdout 防过拟合（只对着固定测试集调）。三集冲突时不是「谁好看听谁的」，而是按固定优先级链判，下面单独说。

**三集是怎么来的、会不会重叠？** 要说实话：**角色不是用例里的字段，是三份独立的用例文件**——评测时分别传给三个参数，你把它放在哪个文件里它就扮演哪个角色，系统不认字段。**系统也不查跨集重复**：同一个用例同时出现在 improvement 和 regression 里，会被按两个角色各判一次、各算一次指标，没有任何去重或告警。这是治理层面的缺口——三集互斥完全靠人维护。**空集不是「跳过」也不是「拒绝准出」，是根本进不来**：三个文件缺任何一个报「缺少 required 数据集」、任何一个为空报「数据集不能为空」，任务在启动时就失败，不会跑出一个半截结论。我认为这样比默默跳过安全，因为「没配 improvement 集」如果静默变成免检，等于把准出门槛关掉了。**移出用例的后果也要认**：把一条用例从回归集搬到别处，对它原来那一集来说这条就是「缺失」，恢复旧运行时会被判为数据集不一致、拒绝复用——历史对比会出现一段空缺，这是改用例数据的必然代价，不是系统级豁免。

**回归优先是不是一刀切？** 默认就是一刀切，这点别模糊：`require_regression_pass=true` 时，候选在回归集里**不能有任何硬失败**——注意是「这一集不能有硬失败」，不是「新增回归为零」；再叠上一条「回归集通过率下降无条件拦」，所以默认对回归是绝对零容忍。**想放宽，先接受一个事实：在回归集上，条数上限基本轮不到生效。** 因为净通过率下降那条是无条件检查，关掉全过开关、配了 `maximum_task_regressions=2`，只要挂一条、没同时恢复一条，`delta` 就是负的，照样回滚——条数上限只在「一进一出、净持平」时才可能轮到它判断。所以 `maximum_task_regressions` 的独立价值主要在 **improvement 集**（那一集不检查全过、也不检查通过率下降），不是「给回归集开一扇放宽的门」。**别把「配两步就能放宽回归」说成结论**，第二步只对净持平有效。**还有一个更严的细节**：全过开关看的是候选集的硬失败**总数**，不是「新增回归」——所以基线本来就挂着的那条用例，在默认配置下同样会让候选回滚。**这种历史遗留怎么「单独放行」要说实话**：系统没有按用例的豁免名单，能做到的只有关掉全过开关（这时整集硬失败都不再单独拦，只靠净通过率和条数上限兜）、或者把那条用例修好/移出回归集——粒度是整集或用例数据，不是「这一条特批」。**还要诚实一点**：我没有给用例打「历史上不稳定」的 flaky 标记，非确定性用例靠一致性层暴露 + 样本量阈值兜底，这是缺口。

**三集冲突到底怎么判？有没有决策矩阵？** 有，而且是一条固定优先级的判定链，不是加权打分：**① 先看回滚条件**——版本身份或版本号对不上、任一集的 run 没跑完、regression 有硬失败或硬通过率下降或软告警超限、holdout 硬通过率下降超过允许值（默认 0）或软告警增量超限（默认 0）、场景门禁或质量门禁不达标，命中任意一条就 rollback；**② 再看拒绝条件**——目标指标没达成，就 reject；**③ 再看有没有改善证据**——默认要求候选必须证明有改善（improvement 集硬通过率上升、或软告警下降、或目标指标改善），拿不出证据就 reject，理由是「没有可度量的改善」；**④ 全过才 accept**。几个关键默认值记住就能答场景题：**回归集零硬失败**、holdout 不要求全过但不许通过率下降、improvement 必须有可度量改善。所以两个最容易答错的场景：「回归集挂了一条」——哪怕只有一条，默认也是 **rollback**，不是 accept；「什么都过了但 improvement 没升也没降」是 **reject**，理由是没有可度量改善。

**这条链还有两个容易漏的机制细节。** 一是**短路**：命中任一 rollback 条件就直接返回，后面的 reject 条件和改善证据都不再评估，报告里也只有回滚原因——「run 没跑完」时你无法从那轮报告里知道候选到底有没有改善，这是故意的（结论不可信时谈改善没意义），但要知道这个信息是被丢掉的。二是「通过率下降」里说的**通过率特指硬通过率**：软告警不进通过率的分母分子，它单独走「软告警增量」这条检查，所以「软告警变多把总通过率拉低了」不会触发通过率下降，只会触发软告警超限（如果超了）。

**这里必须主动认一个缺口：improvement 集自己退化了，决策链不管。** 「通过率下降」这条只对 regression 集检查，improvement 集既不查全过、也不查通过率下降——它只回答「有没有改善证据」。所以构造一个反例是成立的：improvement 集硬通过率从 90% 掉到 80%、软告警从 5 条涨到 10 条，但它配的质量分从 0.8 涨到 0.9 达到了最低改善线，而回归集和 holdout 都没退化 → **按现在的实现在 accept**。我的辩解是「improvement 集的职责是证明变好，protected 的性质由 regression 和 holdout 承担」，但这条反例说明这个分工在「同一集内部指标互相矛盾」时兜不住：要兜住得给 improvement 集也配一条质量门禁或目标指标退化上限（可以配，但默认没配）。**别把「improvement 集退化会被拦」说成既有能力**。

**holdout 挂一条也回滚？比 regression 还严？** 默认是，而且比你想的还严一格：**允许下降的默认值是 0**，所以通过率只要跌一点就回滚，没有「净持平」这种例外（regression 至少还能靠条数上限在「一进一出」时放行，holdout 默认连条数上限都没配）；另外 **holdout 的软告警允许增量默认也是 0**，也就是软告警涨一条同样回滚。取这个值的原因是它的角色是防过拟合的最后一道，宁可严也不能让它慢慢被磨松。**要放宽的做法是给 holdout 配质量门禁或场景门禁**（比如最多允许几条回归、某个高风险场景单独定制），不是把默认值改大——改默认值会把「所有集一起松」变成习惯。

**这条链里几个词各指什么？** 这是最容易被逐个追问的地方，一个词一句：
- **场景门禁**：按业务场景（`scenario` 字段）单独设阈值，防止小切片被整体通过率掩盖——配这个场景最少多少条用例、最低通过率多少、通过率最多跌多少、软告警最多涨多少。典型用法是给「高风险场景」配 100% 通过率。**`scenario` 是用例数据里自带的字段**，用例没写这个字段时会被归到 `default` 场景；所以没配 `default` 的门禁，这些用例就不受场景门禁约束——门禁是 opt-in 的，代价是漏标会让高风险用例逃出检查，这靠用例评审兜，不是系统能发现的。**两个「样本不足」别混为一谈**：场景门禁的「最少用例数」不足，和配了质量门禁时的 `minimum_samples` 不足，**走的都是回滚通道**——都是「门槛没法判定，所以不能自动准出」；区别只是一个按场景计数、一个按数据集角色计数。还有更硬的一档：**你配了某个场景的门禁、但这一集里根本没评到那个场景，也直接回滚**（报「配置的场景缺失」），不是静默跳过——因为「我要求查的场景没查到」比「查了没过」更不能放行。
- **质量门禁**：按数据集角色（improvement / regression / holdout）设**绝对**门槛，问的是「候选自己够不够格」而不是「比基线好多少」——最低硬通过率、最多允许几条回归、最多允许几条关键回归、最少要评多少条用例。
- **目标指标**：按名字配一个业务指标（比如质量分、延迟 p95），带方向和聚合方式，再配「最少要改善多少」「最多允许退化多少」「绝对上限多少」。三个阈值的性质要说清，别混成一样：**「最少改善」和「最多退化」是相对基线的差值，「绝对上限」是候选指标值本身的天花板**（比如 p95 不得超过 500ms，跟基线多少无关）。**适用的集合也不同**：绝对上限和最多退化对三个集都检查（防止某一集里指标爆掉），**只有「最少改善」只在 improvement 集检查**——因为只有那一集是用来证明「变好了」的。还有一条要主动讲：**配了多个目标指标时是「全部都要达到最低线」的与关系**，没有加权、也没有「达到 N 个即可」的配置——所以「质量分大幅改善、延迟只差一点没到线」的结果是 reject，理由是最低改善未达成，不是 accept。这是有意的（目标指标是硬承诺，不是打分），但要知道它是一票否决。
- 三个都是**默认空**，不配就不参与判定；默认生效的只有那三个布尔和数值开关。这个要说，否则会被认为「你以为配了其实没跑」。

**「可度量的改善」到底怎么算？** **三条路，一条都不能漏**：improvement 集的**硬通过率上升**、**软告警条数下降**、或者**配了的目标指标确实改善了**（在 improvement 集上算出的改善量大于零）。**三条是「或」的关系，任一成立就算有改善，不要求同时满足**——所以「通过率没动、但软告警少了两条」是 accept 不是 reject。第三条最容易答漏——只要目标指标的改善量是正的，它就进改善证据，所以「配了质量分、最少改善 0.05，实际从 0.8 到 0.9」这种情况是算改善的，不会被「没有可度量改善」拒掉；但如果改善幅度没达到你配的那条最低线，它会在更前面就被 reject（理由是最低改善未达成），而不是归到「没证据」——**「没到最低线」和「没有改善证据」是两件事，别混着说**。

顺带把软告警说准，它**不是一份固定指标清单**，而是「所有配成 soft 或 candidate 级别的检查里、没通过的条数之和」——某个指标算不算软告警，取决于规则怎么配，不取决于指标本身。所以「延迟降了 50% 算不算改善」要分情况答：延迟既不是软告警规则、也没配成目标指标，那它**不进改善证据**；配成目标指标才进。**「软告警超限」具体在两处查**：回归集比基线涨了超过允许条数、以及场景门禁里配的增量上限——**improvement 集没有这条检查**。所以「improvement 集硬通过率上升、软告警同时也涨了」按现状仍是 accept：软告警在 improvement 集只被当作「下降就是加分」，涨了不扣分。这个不对称要自己先讲出来，别等面试官构造。

**然后必须承认两个缺口**：一是通过率那两条路没有最小提升幅度门槛，从 99.9% 到 100% 也算改善；二是没有显著性检验，improvement 集只有十几条用例时，翻一条就算「上升」。目标指标这条有你配的最低改善线兜着，前两条没有——这是真实的能力边界，别被追问时才想起来。

**「一致性还是很差、只是比上一版少两条告警，也算改善吗？」** 按现在的实现，**算**，而且这里要主动认一个缺口：软告警相关的判定全都是**相对基线**的增量——回归集的软告警比基线多就回滚、场景门禁限制的是增量、improvement 集减少就算证据，但**没有任何地方检查软告警的绝对条数**（质量门禁只有硬通过率和回归条数，没有软告警上限）。所以一个版本告警从 50 条降到 48 条，只要没比基线更差、硬门禁都过，它可以 accept。正确说法是「改善证据是相对的，绝对质量要靠人配目标指标或场景门禁去约束」；**别答成「绝对条数超限会先拦」——实现里没有这个检查**。

**阈值怎么定、能配吗？** 要分两层说，别混：**规则级**的严重级别是可配的——同一条规则可以只记录、只告警或直接拦（拦就是 hard，进硬通过率）；**策略级**的门禁阈值也是可配的——场景门禁、质量门禁、目标指标都是策略文件里的数组，团队按风险偏好加条目。默认策略是保守的一套：回归零容忍、holdout 只禁下降、improvement 必须有改善；门禁数组默认是空的，要用就得显式加。

**rollback 和 reject 的区别？** 用一句话贯穿，别中途换口径：**rollback = 不能自动准出，必须有人看一眼决定是重跑/补数据还是退回稳定版；reject = 结论是可信的，就是没证明变好。** **别把「退回稳定版」写进 rollback 的定义里**——这是上一版的说法，顺着规则推两步就自相矛盾：run 没跑完也归 rollback，可这时正确动作是重跑，还没证明候选好坏就回退是错的。实际实现里 rollback 是一个决策码，底下压着两种流程含义：**不可信类**（身份或版本不符、任一集 run 没跑完、必需指标缺失、门禁因为没评到用例而无法判定）后续动作是重跑或补数据；**不准出类**（硬失败、通过率下降、软告警超限、目标指标超绝对上限或超退化上限、门禁不达标）后续动作才是回退。**这两类在决策码上是同一个值**（CI 拿到的都是 1），只能从 `reasons` 的文案里区分——这是出口粒度不够的真实缺口，不是设计得有层次。reject 只留「所有门禁都过了、结论可信、就是没看到改善」这一类。**「破坏了不能坏的」是最初的设计意图，实现上演化宽了，别再拿它当定义讲**，否则一致性硬失败走 rollback 就自相矛盾。最终发布由人或 CI 执行，系统只给决策、证据和退出码。**决策到退出码是二值的**：accept 是 0，reject 和 rollback 都是 1——CI 层面只区分「放行 / 不放行」，reject 和 rollback 的差别体现在报告和后续动作上，不在退出码上。**第三种退出码（需要人工复核）在设计契约里有，但评测决策链不产生它**，代码里 2 的可见路径目前只有用法和参数校验，这是缺口，别把它说成已实现。

**硬门禁全过、只有一致性在报警，CI 拿到哪个退出码？** 说实话是「正常」。因为退出码只看门禁和最终决策，而一致性默认不进决策——它只往复核队列里塞候选。这是当前设计的真实缺口：「准入资格」这件事目前只体现在质量门禁的样本量阈值上（配了门禁、样本不够会进 rollback），并**没有**把「一致性告警」映射成「需要人工复核」这个退出码。补法也清楚：把关键的一致性规则配成硬门禁级别，它自然会进决策和退出码；但不该默认这么干，否则不稳定会被当成变差。**这里有个容易说错的细节**：一致性配成硬门禁后拿到的是 **1（rollback）**，不是 2——它是硬失败，走的是回滚通道，而 2 在实现里没有评测路径会返回。

**LCS 对齐的是什么？** 对齐的是「步骤签名」——模块加动作，不是原始 ID 或时间戳。**签名不是对齐时临时猜的**，它是归一化阶段就产出的结构化字段，对齐只负责拿它做序列比较；忽略哪些噪音字段也是可配的。序列本身按落盘顺序走，比对前不重排。**为什么不用逐位比**：前面多一步或少一步，后面全部错位，首错会误报在第一步。**为什么不用编辑距离**：要定义替换代价，解释成本高；LCS 的「锚点 + 缺口」好讲也好验证。

**签名里的参数怎么比？自由文本怎么办？** 参数走**结构化子集匹配**，不比整段文本——期望里写哪几个字段就比哪几个，其余不管。明确不做语义等价判断：自由文本的语义是不是同一件事，交给一致性层和反馈层去报警，不放进对齐。否则对齐本身就成了非确定性的，首错也就不可复现了。新增工具不需要改对齐逻辑，只要适配器把它映射成模块+动作就行。**期望字段是谁写的要讲清**：是用例规则里自己声明的，没有「工具级默认字段集」这层机制；所以漏写关键参数（比如只期望了收款方、没期望金额）就会漏判——这属于用例评审要拦的问题，不是对齐层能兜的，别把责任推给算法。

**为什么不重跑 Agent？** 三个原因：非确定性（重跑得到的不是同一条轨迹）、成本（模型调用贵且慢）、副作用（工具可能改外部状态）。落盘结果就是当时的事实，直接拿来对齐更可信。

**两次轨迹都不一样怎么办？** 那本身就是信号——说明这个 Agent 不稳定。系统会给出大量分歧，一致性层也会报警，交人工判断，而不是硬凑一个结论。如果轨迹完全一致但用例还是挂了，就明确输出「没有可见分歧」，说明问题在规则或执行完整性，不在步骤里。

**那首错定位在什么情况下真的有用？** 差异稀疏的时候——两次轨迹大部分步骤相同、只有几步分叉，它能直接把排查范围收到那一步，价值最明确。差异密集时它退化成一份差异清单（报告里能看出分歧数量很大），这时候系统**不会**自动提示「建议转一致性复核」，也没做「差异太多就别看首错」的识别——这是产品层的缺口，讲的时候要自己点出来，别把功能说成永远有效。

**定位到之后还给了什么？** 这里有三个不同粒度，别混着说：**用例级**是状态迁移（哪些用例从通过变失败、从失败变通过）；**单条轨迹级**是首错，也就是第一个出现分歧的步骤；**版本级**是失败聚类——按用例角色、差异类别、模块、动作把同类失败归并成一簇，每簇给条数和前几个样例，报告里有专门一节。聚类结果只做人看的归并，**不做自动归因**。

**为什么强调「可见」？** 因为它只能证明「这里出现了差异」，不能证明「这就是原因」。它是排障起点，不是因果结论，也不参与门禁。

**轨迹太大、触发降级之后，结果还能信吗？** 先给数：两侧步骤数任何一边超过**三百步**就降级，改成按位置比。降级不静默——结果里会显式标注这次是按签名对齐还是按位置对齐，看报告的人一眼知道精度变了。**为什么要降级，不是偷懒**：LCS 的动态规划表是 n×m 的整数矩阵，三百步是九万格，还能接受；三千步就是九百万格、几十兆内存，单条轨迹就能把进程拖垮。按位置比是线性的，至少能给出一个确定性结果并把「精度下降」标出来。**为什么不改用分块 LCS 或窗口对齐**：那确实更好，是明确的改进方向，但我没做——现在的取舍是「保证有上界，宁可精度降也要出结果」，不是「这个降级方案已经够好」。降级率高说明上限该调，不过我没有单独做降级率的看板，这也是可以补的。

**首错准确率多少？** 没有人工标注集，不报命中率。能说的是：结果是可解释的差异清单加失败聚类，差异稀疏时通常只需要看开头一两条就能定性，最终判断由人做。**「一两步」这个说法要给清楚边界**：它是差异稀疏场景下的量级描述，不是我统计出来的平均值；差异密集的时候它给的是几十条差异的清单，不会缩到一两步。所以别把它讲成一个指标。

### 2. 统一接入与归一化

**为什么要统一？** 没有统一层，评测、对比、诊断三套逻辑都要各自适配不同框架，接一个新框架要改三处。统一成一种轨迹后，下游全部解耦。

**契约抽象了什么？** 四件事：怎么调用 Agent、怎么读它的轨迹、哪些是硬门禁、哪些是软质量。核心只认归一化后的轨迹，原始轨迹保留做证据。

**各框架必填字段不一样，完整性怎么统一？** 契约钉死一个最小完整集——轨迹标识、最终输出、事件列表是硬条件，其余都进扩展字段留给领域规则。映射不上就是缺失，由结构层拦下来。不搞「适配器声明自己支持哪些字段」那套，因为不能对齐比较的字段对评测没有意义，统一最小集才是可比较的前提。

**扩展字段有没有 schema、跨框架能对上吗？** 没有强 schema，是自由键值，规则按名字取值。在同一个适配器内部它是稳定的，**但跨适配器不保证语义一致**——A 框架的 `score` 和 B 框架的 `score` 可能不是一个东西。这是有意留的弹性：主流框架的业务字段差异太大，硬统一只会逼适配器造假字段。代价要讲清：**下游不能拿扩展字段做跨框架对比**，跨框架能比的只有最小完整集和签名序列；要跨框架比业务指标，得先约定同名同义，这一步现在靠人。

**怎么保证新写的适配器真的符合契约？** 目前没有专门的适配器契约测试套件，这一点要说清楚。实际的验收线是结构层和行为层：新适配器的轨迹必须过最小完整集和工具序列规则，过不了就是映射写错了。这比单测更接近真实约束。

**四类接入的难点分别是什么？** Java 适配器要处理类加载和依赖隔离；HTTP 要处理超时、重试和状态轮询；离线文件是解析多种导出格式，还要兼容不同的包装层级；AgentScope 是事件类型比较明确，做一层映射就行，独立成模块不污染核心。

**归一化丢了信息怎么办？** 保留原始轨迹做对照；关键字段缺失就留空并纳入结构层检查，不猜、不补默认值——默认值会造成假一致。

**并发和乱序怎么办？** 这里我必须说准，不能含糊：**LCS 本身就是序列算法，它依赖顺序**。所以真正的问题不是「不依赖顺序」，而是「序列怎么来」——序列就是归一化之后事件数组的顺序，适配器按什么顺序写进来就是什么顺序，我没有在比对前再做一次排序。忽略的是 span_id、时间戳这类噪音**字段**，不是顺序。代价要说清：同一层级的并发步骤如果顺序本身不稳定，LCS 结果也会跟着不稳，这是首错可信度的真实边界；能兜的是——适配器按调用链落事件、对齐只在同一份落盘顺序上做、差异密度过高时明确降级成清单而不是硬给一个「首错」。

**新增一个框架要改什么？** 只加一个适配器，核心零改动。**前提得说清**：这个框架要能提供契约的最小完整集——轨迹标识、最终输出、事件列表。提供不了的（比如只有一个最终答案、没有过程）不在接入范围内；这是接入边界，不是靠改核心去兼容它。别把「零改动」讲成「什么框架都能接」。

**适配器出错怎么办？** 解析失败要能定位到具体哪一条、哪类字段；整条不可用时按接入失败处理，不让残缺数据静默进入评测——宁可不评，也不要假通过。

**敏感数据怎么处理？** 落盘和发给 reviewer 前统一脱敏：凭据类键（authorization/api_key/password 等）、`Bearer`/`sk-` 字符串、邮箱、大陆手机号、18 位居民身份证都会被掩码；规则和指标仍在原始 trace 上计算。**边界**：这是保守正则，不覆盖地址、银行卡、国际手机号，组织仍需在 ingest 层按字段语义补。

### 3. 异步调度与资产回流

**为什么要异步？** 评测是分钟级的，HTTP 请求不能一直挂着；提交后立刻返回任务号，worker 后台跑，页面轮询状态。

**为什么自研？** 定位是轻量、可嵌 CI，引入中间件会抬高部署成本。文件存储开箱即用、方便人肉排查；数据库存储支持多实例共享。两套各自独立，不做双写。

**租约怎么防重复执行？** worker 领取任务是原子的，领到就有租约，靠心跳续租；租约过期其他 worker 才能回收，原子领取保证不会两个人同时干同一个任务。心跳偶尔异常不会立刻停任务，避免网络抖动误杀；真正过期才交给别人。

**心跳和任务执行是同一个线程吗？** 不是，这是设计里明确分开的一点：心跳跑在**独立的一个调度线程**上，任务线程只管跑评测。原因就是你说的那个坑——一条用例里如果有几次长调用，加起来可能超过一个租约周期；心跳要是跟执行串在一起，调用期间发不出心跳，租约就会被别人抢走，同一个任务被跑两遍。分成两个线程之后，续租时钟和任务耗时无关。另外两种失败要分开：**续租被拒绝**（说明别人已经接管）会置一个取消标志并中断当前任务线程；**存储瞬时故障**只记一条日志、等下一个周期重试，不会因为一次抖动就把健康任务停掉。

**中断真能让它立刻停吗？两个 worker 会不会同时写？** 要老实说，不能夸成立刻停，而且要分两层：**「不再派新活」是即时的**——真正跑评测的那个线程是在「等下一个用例结果」的位置阻塞的，中断信号打上去立刻抛出来，整轮中止、任务状态马上变成已取消，一批还没攒满的结果直接丢弃（不落盘）。**「已经在飞的调用真的停下」不保证**——中断会再传给工作线程池，但阻塞在 socket 读或等子进程上的调用不一定响应中断，得靠**这次调用自己的超时**退出，所以这一段最坏延迟是一次调用超时。这期间那个已经过期的 worker 就算还在跑，也写不进去：同一个运行目录有跨进程写锁，加上恢复前的身份校验，它的写入会被挡住。所以准确说法是「取消 = 停止派新活 + 丢弃在飞结果，可能白跑一段，但不会和新 worker 的数据混」。

**租约多久、心跳多久，这个数怎么定的？** 租约一分钟，心跳按租约的三分之一续，也就是二十秒一次。取这个值的权衡是两头：太短，网络抖一下就误判 worker 死了；太长，真挂了要等很久才回收。二十秒一次意味着一分钟内能白丢两次心跳还没被抢——留的就是两次重试窗口。

**过期回收之后，重跑是从头还是接着跑？** 要分两个粒度说，不然容易含混：**写入动作是按批的**——三十二条结果先在内存里拼成一个整块，一次追加到文件，不是一条一条 flush；**恢复判断是按 case 的**——恢复时逐条问「这个用例有没有已落盘的结果」，有就跳过，没有才跑。**那批写到一半崩了算什么？** 一次追加并不是原子操作，可能一行没写、可能写了一半。所以实际结果是：已经完整写进去的那些行，恢复时会被读到并跳过；只有写了一半的那一行会被截断、连同后面没写的一起重跑。这正是「尾部修复」要存在的原因——批量追加本身不保证原子。所以别把它讲成「整批重跑」或「逐条落盘」，两个都不准：**批是写入的单位，case 是恢复判断的单位**。

**批次恢复和幂等键是一回事吗？** 不是，两者正交、管的是不同层。**恢复（逐 case 判断已落盘结果）发生在任务内部**——租约过期、被别的 worker 接管之后，新 worker 靠运行目录里已落盘的结果决定从哪接着跑。**幂等键在提交层**——防的是调用方重复提交产生两个任务，同键命中已有任务、同键不同内容报冲突。一个在「跑的时候」，一个在「提交的时候」，不交叉。所以「用户用同一个键重新提交」拿到的是旧任务，不会触发恢复；恢复只发生在同一个任务被重新领取时。

**旧 worker 复活会不会重复写？** 会重复执行，但写不进去——恢复前要校验运行身份和数据集一致性，同一个运行目录还有跨进程写锁，过期 worker 的写入会被挡住。

**at-least-once 会重复跑，数据会不会串？** 不会。任务里固定运行身份，恢复时校验数据集和配置（用清单哈希），不一致就拒绝复用而不是接着写；同一运行目录有写锁。重复执行最多白跑一次，不会把两次结果混在一起。

**为什么不承诺 exactly-once？** 跨进程的精确一次成本极高，要分布式事务。用「身份 + 校验 + 锁」把正确性补回来，比假装精确一次更诚实。

**幂等键到底是什么、谁给的？** 是**调用方传进来的键**，不是内容哈希——命令行有对应的可选参数，系统根据这个键派生出稳定的运行标识，所以同一个键重试得到同一个标识，不依赖时钟。同一个键配不同内容直接报冲突、不覆盖，因为静默返回旧任务会让人以为新参数已经生效；键为空就退回普通（非幂等）提交。**「不同内容」到底比什么，要说准**：比的是**整份提交参数**（规范化后逐字段全等），不是「只比影响结论的输入」——适配器、用例路径、输出目录、worker 数、重试和超时策略、预算都在里面，所以你把 worker 数从 8 改成 16 再去重试，也会被判成冲突。反过来**它不含数据集的内容指纹**：数据集文件内容改了、路径没改，不会报冲突，而是直接命中旧任务返回旧结果。这两条合起来说明幂等键的定位是「防重复提交」，不是「防用错参数」——后者得靠数据集哈希在恢复时校验。**一句实话**：Dashboard 一键提交没有独立幂等键，连点两次会建两个任务，这是已知缺口，不是「前后端双保险」。**被问「那怎么补」别卡住**：让提交页在表单初始化时生成一个键、两次点击复用同一个键，再配按钮禁用做第二道；注意键不能在「每次点击时」现生成，那样两次点击就是两个键，等于没做。现在这两道都没有。

**同一个 commit 重跑 CI，会拿到旧结果吗？** 会——键相同就是同一个任务，返回的是已经存在的那个，包括它失败的状态。所以「拿 commit 号当键」只适合防止重复触发，不适合修完基础设施后重跑；想真重跑就换一个键（加流水号或时间戳）。我没有做「强制覆盖」这个逃生口，是有意的：静默覆盖会让「同一个键两次跑出不同结论」更难查。

**换键重跑之后，旧任务堆着怎么办？** 这是个真实的产品缺口，分开说：**产物目录**有清理命令，可以按时间截止加「保留最近 N 个」来 prune，而且支持 dry-run 先看会删什么；**任务记录本身没有删除或归档**，同一个 commit 会对应多条任务，只能看创建时间和状态人工判断哪条是最终结论。要补的话是「按 commit 或按标签归档」这类索引，现在没有。

**哪些错误会重试？** 先分两层，再纠正一个常见误解：**任务层的重试不是按错误类型分类的**。适配器调用层是 `--retries`（默认 0，不重试），任务层是 `--max-attempts`（命令行提交默认 3，Spring 配置里默认 1），打开后指数退避加抖动。但捕获到的异常一律按可重试处理，**不区分「瞬时错误」和「配置错误」**——真开了重试，配置错也会白重试一次，这也是默认关掉它的原因之一。真正直接走终态、不进重试的是「已经有结论」那一类，而它的判定随入口不同：**服务端队列**里跑完并产出结论就算任务成功（哪怕结论是 reject），只有执行过程抛异常才重试；**命令行 worker** 把评测当子进程跑，退出码非零（包括候选被拒）就直接标失败终态，也不重试。所以「重试」在这套系统里只处理执行中断，不处理业务结论。

**任务能取消吗？worker 卡死怎么办？** 排队中的直接取消；运行中的是协作式取消——取消请求写进任务记录，**由心跳线程下一个周期（最长二十秒）发现**，发现后立刻中断任务线程，避免强杀导致写了一半。所以「多久能开始停」的上限是一个心跳周期，「在飞的调用什么时候真停」取决于它自己响不响应中断，最坏等到单次调用超时——这两段延迟要分开讲，别合成一个数。**卡死这个漏洞要说清**：没有「任务级最大运行时长」这种硬砍机制，真正的兜底是两件事——单次 Agent 调用有超时（默认三十秒，**可配**，慢 Agent 就按场景调，不是写死的），租约到期会被别的 worker 回收。**杀进程树要说准是哪个超时**：就是单次调用这个超时，杀的是**这一次调用自己启动的那棵进程树**，不是整个 worker，也不影响同批其他并发调用——每次调用是独立进程。实现上是先杀子孙再杀父进程，顺序不能反，父进程一死，子进程会被系统重新挂到别处，我们就找不到了。**这个做法的边界也要认**：枚举的是杀的那一刻的子孙，父进程在被杀前又 fork 出来的新进程，极端情况下可能漏掉、被系统接管；真正的兜底是容器级别的 cgroup 整组回收，我没做。半截状态靠身份校验 + 写锁挡住，和租约回收走同一套恢复路径，不另开分支。

**积压了怎么办？** 先看是任务多还是 worker 少：加 worker、把长任务拆细；同时页面能看到排队数和预计等待，避免人以为卡死。

**双存储谁是准的？** 两套各自独立，不存在双写问题；业务判定逻辑抽成公共部分，用同一套契约测试跑两个实现，保证同一批评测两种存储结论一致。

**人工复核怎么变成可复用的数据？** 复核结论是结构化存的，不是写在报告里——带结论、角色、复核历史。归档时按 improvement/regression/holdout 标角色，导出格式和评测数据集一致，下一轮直接就能用，不需要转换。回流就是数据集文件更新了这条普通链路。

**回流会不会污染 holdout？** 分两层说。**合成/对抗用例已有系统级边界**（2026-11）：`source=synthetic|adversarial` 只允许出现在 improvement，出现在 regression/holdout 直接 rollback；还可配 `synthetic_ratio_cap` 和 `require_provenance`。**人工复核导出仍靠流程约束**：归档带角色标记，但不能阻止有人把复核数据放进 holdout。holdout 的读权限隔离仍是明确缺口；内容哈希只能做事后检测，不是泄漏检测器。

**飞轮转起来了吗？** 诚实说：目前示例数据只有一两行，没有存量回归集，算不出提升百分比。补法也清楚——跑一轮复核到归档，就第一次有了分子分母。

## 三、十个杀手问题（一句话接）

1. **对齐的元素是什么、怎么判相等？** 步骤签名（模块+动作），归一化阶段就产出；参数走结构化子集匹配，忽略 ID 和时间戳这类字段。要说准：**LCS 依赖序列顺序**，序列就是归一化后事件的落盘顺序，不是「不依赖顺序」。
2. **轨迹不完整或 ID 不稳定，首错还可信吗？** 正因 ID 不稳定才按内容签名对齐；完整性本身是结构层的检查项，截断或缺失会被拦下而不是假装对齐成功。并发步骤顺序不稳定时，首错可信度会下降——这是边界，不是嘴上抹过去。
3. **四层怎么聚合？** 不加权求和，是固定优先级：先看回滚条件（身份不符、run 不完整、回归集有硬失败或通过率下降、holdout 下降超限、场景与质量门禁不达标），再看拒绝条件（目标未达成），再看**有没有可度量的改善**（默认必须证明有改善），全过才 accept。补一句最容易漏的：回归是**零硬失败**，不是「新增回归为零」。
4. **怎么证明隔离了非确定性？** 硬门禁是纯函数，只收确定性信号，同输入同版本结论唯一；不确定的来源单独放一致性层，默认只报警。样本量不足时拒绝自动准出这条能力有，但要配质量门禁才生效；默认策略下没有样本量门槛，这是要承认的。
5. **旧 worker 复活会不会重复写？** 租约过期后原 worker 的写入会被身份校验和写锁挡住，它复活也写不进去。
6. **双存储不一致怎么办？** 不存在双写，所以没有同步问题；语义一致性靠同一套契约测试保证，测试跑两个实现。
7. **幂等键是什么？重试副作用怎么办？** 调用方传的键，派生稳定标识，同键不同内容报冲突不覆盖；重试走恢复，先校验数据集和配置一致，不一致就重跑而不是复用。
8. **holdout 怎么防污染？** 目标版本和身份先校验，人工归档带角色标记，流程上不许复核数据随意进 holdout；内容哈希只能做事后检测，系统级隔离是缺口。
9. **首错准确率多少？** 没有人工标注集，不报 Top-1 命中率；能说的是差异稀疏时可以把人直接带到开头几条差异，差异密集时给的是清单，定性由人做。
10. **决策自动还是人工？** 系统给决策、证据和退出码；执行由人或 CI。误判成本落在发布环节，所以收货权一直在人手里。

## 四、高频追问补充

- **轨迹存哪里？** 文件存储是默认，**一行一条用例（JSONL）**，便于追加和断点恢复；数据库存储用于多实例。大轨迹按批落盘，不一次性读进内存。
- **一行写坏了怎么恢复？** 三条规则：只允许最后一行没写完时截断它；完整但缺换行的补分隔符；UTF-8 被截成半个字符能恢复。**中间行损坏不猜，直接报错**——猜出来的数据比没有数据更危险。整套是用临时目录构造坏文件验证的。
- **一条轨迹特别大怎么办？** 对齐时有步数上限，超了降级成按位置比并在结果里标注模式，不静默降级；报告里差异条目也做截断，保证体积可控。对齐本来也只装签名序列，不是把原始内容全塞进内存。
- **怎么观测系统自己？** 用监听器接口把生命周期事件抛出去，可接 Micrometer 和 OpenTelemetry；指标标签只用有限集合，不带单次运行的 ID，否则时间序列会爆。监听器自己抛异常不影响评测主流程。
- **系统自己挂了会不会误判？** 读不到数据时分级降级：能查队列就返回队列状态，只能查到落盘记录就返回落盘记录并记告警，都不行才报错——部分可用优于整体不可用，但绝不返回「通过」。
- **测试怎么覆盖？** 单元测试、两个存储的契约测试、集成测试；恢复、并发抢锁、进程树安全这些都有专门测试，数据损坏是用真实构造的坏文件验证的。
- **性能瓶颈在哪？** 归一化和对齐是 CPU 密集，评测调用是 IO 密集；前者靠上限和降级，后者靠并发和异步。
- **谁能改阈值、看 holdout、执行回滚？** 目前是配置和流程层面的约定，没有完整权限体系——这是明确的边界，别说有 RBAC。
- **怎么审计一次决策？** 决策里带全量条件列表、每条的数值对比和证据路径，还带基线/候选的运行血缘（哪个 run 对哪个 run），报告是数据不是日志，人能回看每一步为什么被拦。
- **失败聚类到底怎么聚的？** 不是相似度聚类，就是按四元组分组：数据集角色、差异类别、模块、动作。差异类别是固定枚举：步骤新增、删除、替换、乱序、报错、状态变化、字段变化、最终输出变化。**三个数据集都聚**（improvement、regression、holdout 里发生回归的用例都会进簇，靠角色字段区分），不是只看 regression。报告里是**一张表、第一列就是数据集角色**，没有拆成三张，靠这一列过滤；每簇给命中条数和前五个用例样例。**一个用例只进一个簇**——归簇用的是它的**首个分歧**（差异类别 + 那一步的模块/动作），不是「有几个差异就进几个簇」，所以各簇条数加起来正好等于回归用例数，不会重复计数；代价是一个用例后面还坏了几步时，那些信息只留在明细表里，不进聚类。它只做人看的归并，不做自动归因；更语义化的聚类（比如按向量相似度）是扩展方向，当前没有。**粒度上的代价要认**：因为按「模块 + 动作」分，同一个根因如果落在不同动作上，会被拆到两个簇里，看起来像两类问题；我没有做过聚类质量的人工评估，也没有「合并相近簇」的机制——这一节的价值是排序（哪个簇最大先看哪个），不是保证根因被完整归并。
- **「乱序」这一类是怎么判出来的？** LCS 只能告诉你哪些步骤匹配、哪些没匹配上，光看结果区分不了「改了」和「挪位了」。所以在未匹配的缺口区里再做一个判断：把缺口两侧按位置配对，**如果两个位置的签名相同**，说明这一步不是变了而是移动了，标成「乱序」；签名不同才标成「替换」。这是个后处理规则，不是 LCS 自带的。局限也要说：移动距离很远、又恰好落在不同缺口里时，「乱序」可能被拆成一次删除加一次新增，这时候类别就不准了；**误判率没有量化**，因为没有标注集，只能说这是已知边界。
- **数据集哈希是一整集算一个吗？** 不是，逐用例算（用例标识 → 内容哈希）。恢复时只校验「已经落盘的用例有没有少、有没有被改过」，新增用例直接合并进来照跑，所以往数据集里加一条不会让前面跑过的白费。
- **阈值配置存哪、改错了怎么办？** 存在数据集和策略文件里，跟代码一起走版本控制，改了什么在 diff 里能看见。没有配置中心、没有在线改阈值的界面——这也是权限体系缺位的同一块缺口。**多实例部署有个真实的洞**：每个实例读自己的配置文件，没有「启动时比对配置版本」这种校验。要说准影响面：**同一个任务不会被两个实例同时跑**（租约保证），但同一批提交里的不同任务可能被不同实例领走——于是 A 用例按旧阈值判、B 用例按新阈值判，汇总出来的这一批结论自相矛盾。当前靠「配置跟代码一起发版」这个约定规避，不是靠机制。
- **证据会不会失效？** 会，而且这儿有个**直接的冲突**要承认：决策里带的是文件路径，指向的就是输出目录下的那次运行目录；而清理命令 prune 删的正是同一批运行目录。也就是说 **prune 一开，审计链就断**，清理和审计在存储上没有分离，dry-run 只能让你看见会删什么，防不了误删。我没做证据的独立持久化、内容寻址，也没做证据目录的只读保护或「保留期」策略——审计要求高的场景只能先关掉 prune，把证据单独归档这件事没做。
- **合成用例怎么来的？** 说实话很朴素：两个手写模板——一个单步 echo，一个三步工具链（路由→检索→回答），用序号变化输入和期望，批量展开成万条。所以用例之间结构完全一样、只有输入不同。用途是压系统自身的固定开销（归一化、对齐、队列、存储），**不是**模拟真实业务分布；这也是为什么它只能证明「框架能跑量」，不能证明「评测有效」。**2026-11 的 `assay synth` 是另一条线**：从文档/轨迹生成用例，带质量门、重写上限、3-gram 去重和 provenance；`attack` 生成 9 类对抗用例。它解决的是数据来源，不是压测。
- **第二个 bullet 写「四类接入」，你接过真实框架吗？** 没有，这是个必须自己先说的事实：四类接入里，**HTTP、离线文件、Java 进程内接入这三类是拿示例适配器和集成测试验证的，AgentScope 有自己的独立模块和事件映射，但也没有接过生产上的真实应用**。所以准确的说法是「设计并实现了适配契约、验证了契约可实现」，不是「验证了四个真实框架」。**那契约的说服力从哪来？** 三点：一是把「怎么调、怎么读、哪些硬门禁、哪些软质量」四件事定成了可实现的接口，示例适配器证明这四件事能落地；二是四类接入源的差异（进程外 HTTP、同进程 Java、离线文件、带类型事件）都被映射到了同一个最小完整集，说明这个抽象不是只为某一个框架量身定做的；三是准入边界是硬的——提供不了最小完整集的框架明确不在范围内，而不是含糊地「都能接」。真实框架接入是下一步，我不把它说成已经做过。
- **数据漂移怎么办？** 数据集有版本和内容哈希，恢复和对比时能发现「样本被改过」；再往上要靠定期复核和新增场景覆盖，这块目前没有自动监控。

## 五、反射性问题（诚实回答，别硬撑）

- **规模多大？** 个人项目，本地和单机场景，没有真实生产流量。**10 万条确定性评测已验证**：规则 + `agent-safety` 两项指标，单机 28s、结果约 490MB、4GB 堆；5 万条 15s/2GB，2 万条 7s/1GB，5 千条约 2s。用的是规范事件形态的合成 trace（不是真实 LLM Agent），测的是**端到端**——归一化、规则/指标、落盘、出报告，**不含模型调用**。**这些数只代表框架处理吞吐，不代表真实 Agent 的评测吞吐**——真实瓶颈在模型延迟和供应商限流。G-Eval 建议单批 500–2,000 条，开启缓存和预算。
- **效果有数据吗？** 只有能复现的工程数据（测试规模、覆盖率、基准耗时）；业务类指标没有分母，不编。
- **最大失败案例？** 没有生产事故可讲；能讲的是自己踩过的坑——断点恢复的半行数据、多写者混写、页面在历史报告多了之后变慢，三个都有对应的修复和测试。**页面那个讲细一点更像真的**：报告列表页每次请求都把目录里所有产物重新读一遍算摘要，历史累积到几百个目录之后就明显卡；修法是给摘要加一层内存缓存，key 用文件和「修改时间 + 大小」，两者任一变就重新算——这里的关键不是加缓存，是**判断什么情况下必须失效**，只按文件名缓存就会一直返回旧摘要。**这个失效条件是启发式，边界要认**：如果内容变了但修改时间和大小都没变（同一秒内、同字节数的覆盖），缓存会返回旧值。当前能接受是因为报告产物是追加写或整目录重建，不会做同大小的原地覆盖；将来真支持原地更新，这个 key 就得换成内容哈希。
- **系统还缺什么？** 单机存储、没有多租户和权限、holdout 没有系统级隔离、没有 flaky 标记、没有任务级硬超时、没有真实外部 Agent 验证、诊断只是辅助证据。**再加两条决策出口上的**：决策码只有一个 rollback，没区分「该重跑」和「该回退」；improvement 集自身退化没有检查。**治理层面缺**：三集跨集重复没有系统校验（合成/对抗用例的数据集边界已经强制）；holdout 没有系统级读权限隔离。**执行层面缺**：自由文本 LLM 复核只有宽松 JSON 解析，G-Eval 只校验分数/字段、不是全量 schema；重试不按错误类型分类；PII 只覆盖常见正则；没有 flaky 标记、没有任务级硬超时、没有真实 Agent 的 live 吞吐基准。下一步优先级是存储可扩展、真实 Agent 接入、judge 校准与 live 基准。
- **重做会删掉什么？** 会把「诊断」和「门禁」的边界从一开始就划清——诊断结果永远不进决策，这条越早明确越省事。
- **别人给你一个技术建议，你怎么判断要不要采纳？** 先回代码和实际行为核对，再决定，不按「听起来合理」采纳。举个真实的：评审时有人建议我给文件存储加帧格式（长度前缀加校验和）来防半行数据，我核对了实现——现在是 JSONL 一行一条加尾部修复，帧格式是另一套方案、并不存在，所以没改，只在文档里标注「这条与实现不符」。同样被否掉的还有「任务级最大运行时长」和「一致性稳定性门槛」，都是听起来合理但系统里没有的机制。理由很简单：**方案文档里写没实现的机制，被追问第二次就露馅**，不如当场说清边界。
- **最大收获是什么？** 从「靠直觉写代码」变成「先找确定的边界，再决定哪里能容错」。三个坑是连着长出来的：半行数据教我「边界必须先定义清楚」；多写者混写教我「正确性要有身份和锁兜，不能靠约定」；页面变慢教我「缓存要能失效，不然是在骗自己」。这套思路比任何单个技术点都值钱。

## 七、边界与禁语

- 不说：根因定位、精准因果、生产级、百万级、准确率 99%、自动上线/自动回滚、提升 X%、exactly-once、「形成闭环」。
- 不说「实时接收 OTLP」——是解析离线导出文件。
- 不说「高可用」——说可靠性；单机场景不谈容灾。
- 不说自己有完整权限体系、多租户、分布式调度。
- 不说自己没有的机制：适配器契约测试套件、flaky 标记、任务级最大运行时长、holdout 系统级隔离——一律承认是缺口。
- 不说「LLM 完全不参与判定」——默认复核不进，但可选的 G-Eval 指标能按 hard/soft 参与门禁。
- 不说「10 万条是真实 Agent 吞吐」——那是规则 + 确定性指标的合成 trace 基准，不含模型调用。
- 不说「PII 全量脱敏」——只覆盖凭据、邮箱、大陆手机号、18 位身份证这类保守正则，地址/银行卡等要在 ingest 层补。
- 不说「LCS 不依赖顺序」——它是序列算法，依赖落盘顺序，忽略的只是噪音字段。
- 不说「非关键回归可以挂一两条」——默认要求回归集零硬失败，放宽要先关全过、再配条数上限，而且净通过率不能降。
- 不说「三种退出码对应三种决策」——实际是二值：accept 是 0，reject 和 rollback 都是 1；「需要人工复核」那个码在评测路径上不产生。
- 不说「一致性硬门禁会返回人工复核码」——它返回 1，走的是回滚通道。
- 不说「软告警有绝对条数门槛」——所有软告警判定都是相对基线的增量，绝对质量只能靠目标指标或场景门禁去约束。
- 不说「清理不影响审计」——`prune` 删的运行目录就是证据路径指向的目录，清理和审计在存储上没有分离。
- 不说「同一版本跑两次结论必然一致」——判定是纯函数，但两次运行的轨迹本身不同；确定性适配器下才一致。
- 不说「rollback 就是退回稳定版」——它底下压着「不可信」（该重跑/补数据）和「不准出」（该回退）两类，决策码不区分，只能看 reasons。
- 不说「improvement 集自己退化了也会被拦」——通过率下降只对 regression 检查；improvement 只看有没有改善证据。
- 不说「幂等键是内容指纹」——它比对的是整份提交参数（含输出目录、worker 数），不含数据集内容哈希。
- 不说「取消能立刻停掉所有 Agent 调用」——停止派新活是即时的，在飞调用最坏等自己的超时。
- 不说「所有 LLM 输出走严格 schema」——自由文本复核仍是宽松 JSON + 解析失败标记；G-Eval 只校验 score/字段，不是全量 schema。也不说「LLM 完全没有判定权」——G-Eval 可选门禁。
- 不说「重试按错误类型分类」——捕获到的异常一律进重试，不区分瞬时错误和配置错误；已经有结论的（含候选被拒）不重试。
- 不说自己没用过的技术（虚拟线程、Redis、Kafka）；被问到就说边界，不猜。

## 八、2026-11 新增能力（口述口径）

> 这一节是简历里「指标 / 合成 / 校准 / 规模」的补充；前面的门禁与队列口径不变。

### 1. 指标层

- **指标 = 带分数和理由的检查**：`score / threshold / reason / breakdown / evidence / status`，状态有 `PASS / FAIL / SKIP / ERROR / NOT_EVALUATED`；
- 确定性指标：`tool_permission`（越权是 hard）、`loop_detection`（重复工具/推理停滞/循环序列，soft）；
- 语义指标：G-Eval-lite，先让模型把 criteria 拆成 2–5 条评分步骤，再给 0–10 分并归一化；`strict` 只接受 0/1；
- **失败语义**：模型失败、非法分数是 `ERROR`，没证据是 `SKIP`，两者都不进通过率分母；
- **成本**：指标级缓存（键含 trace、case、指标配置、模型），judge token 计入运行预算，resume 会回填。

### 2. 合成与对抗用例

- `synth`：文档/轨迹 → 切块 → 模型生成 → 质量评分 → 低分带反馈重写 → 仍低分就丢弃（不是保留）→ 3-gram 去重 → 标准 case JSONL；
- `attack`：从已有用例生成 9 类对抗变体（prompt injection、jailbreak、PII 提取、工具滥用等），带 `safe_behavior`、`severity`、`origin_case_id`；
- **数据边界**：`source=synthetic|adversarial` 只允许进 improvement；进 regression/holdout 直接 rollback；可配 `synthetic_ratio_cap` 和 `require_provenance`。

### 3. 评估器校准

- `review` 保存人工结论，`calibrate` 输出混淆矩阵、precision、recall、F1、agreement；
- 人坏/自动坏 = TP；人好/自动坏 = FP（误报）；人坏/自动好 = FN（漏报）；
- `confirmed_badcase` 视为 bad，`accepted` / `false_positive` 视为 good，`needs_follow_up` 暂不计入；
- 指标 `skip/error` 记为 not applicable，不进入矩阵。

### 4. 展示与治理

- Dashboard 有「指标」tab 和指标历史趋势；CLI 有 `--display failing|passing|all`；
- 落盘/评审前做凭据和常见 PII 脱敏；run metadata 记录 `dataset_hash`；
- 演化目标可以写 `metric:<name>`，把指标分纳入 accept/reject。

### 5. 规模口径

- 10 万条规则 + `agent-safety`：单机约 28s、490MB 结果、4GB 堆；5 万 15s/2GB，2 万 7s/1GB；
- 这是确定性合成 trace 的框架吞吐，**不是真实 LLM Agent 吞吐**；
- G-Eval 建议单批 500–2,000，按供应商限流和预算调。

## 九、新增能力追问（一句话接）

1. **指标和规则有什么区别？** 规则回答「有没有」，指标回答「多少分、为什么」；指标结果会映射成 hard/soft 检查，复用同一套门禁。
2. **`SKIP` 和 `ERROR` 为什么不能算通过？** 没测到和测失败都不能伪装成好结果；两者都不进通过率分母，报告单列。
3. **G-Eval 会不会引入非确定性？** 会，所以它是 opt-in；失败是 `ERROR`，strict 是 0/1，缓存键包含模型和配置，预算限制 judge 调用。
4. **缓存键包含什么？** trace 内容、case、指标名与配置指纹、模型；改 trace 或配置必然失效。
5. **合成用例怎么防低质和重复？** 质量分低于阈值先重写，重试耗尽就丢弃；再做 3-gram 去重，重复项计数而不是写入。
6. **为什么合成用例只能进 improvement？** regression/holdout 是可信证据；合成数据进去会让候选在自己调过的数据上被评判。系统直接 rollback。
7. **precision 和 recall 分别说明什么？** precision 是自动标记里人真正认为坏的比例（误报少）；recall 是人认为坏的里面自动抓到的比例（漏报少）。
8. **10 万条是怎么跑的？** 规范事件形态的合成 trace + 确定性指标，不含真实模型；换成真实 Agent 后瓶颈在模型调用。
9. **GEPA 优化器负责什么？** 只根据诊断生成完整候选（GEPA 默认 2 个、COPRO 4 个，做相似度去重）；accept/reject 仍由演化策略决定。
10. **脱敏能保证合规吗？** 不能。它覆盖凭据和常见 PII 正则，地址、银行卡、国际号码等要在 ingest 层按组织规则补。
