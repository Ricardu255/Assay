# 模拟面试 19 题覆盖审查 + 全文问答分类地图

> 本文是 `assay-interview-prep.md`（整合版）的**索引与缺口清单**，不替代原文；所有应答细节以 prep 对应章节为准，数字一律按「快速口径速查」。
> 背景：对照外部模拟面试清单（19 题，五大板块）逐题审查；结论是 **10 题直接覆盖、7 题部分覆盖、2 题缺口**（详见第一节）。
> **实习生岗位校准**：这份清单的问法偏资深工程师/平台 Owner（团队背景、业务收益、多业务线接入、上线后收益）。以实习生身份面试时，商业化与团队运营类问题（Q1 的团队部分、Q16，以及 Q2/Q5 里「多业务线」「数据集很大」的运营侧问法）大概率不会被深问，复习重心放在技术实现题（见第一节末的优先级分组）；个人项目就按个人项目答，不装团队规模。

### 板块二：首错定位与 Trace 对齐

| # | 问题 | 状态 | 现有回答位置 | 说明 / 应答提示 |
|---|---|---|---|---|
| 6 | Trace 数据结构；步骤是否线性；树状/图状怎么办；LCS 复杂度与优化 | ◐ | B2、D1、主题四 4.3 TraceDiff 专题（4.3.2 算法步骤、4.3.4 为什么 LCS、4.3.6 边界案例、4.3.8 追问）、S42 | 复杂度与优化**有**：主题四 4.3.4 明确写「最坏 O(n×m) 时间和内存，所以有 300 步上限；超限退化为 positional 并在 `alignment` 标注」。**缺口：「树状/图状（循环、条件分支）」没有专门答案**。可组织口径：归一化时非线性行为已被适配器展开成 `events` 线性序列（步骤 key 取 `module/action`），嵌套调用用「嵌套连续块」匹配（`sequence_contains` 支持）；循环展开后就是重复步骤，由 `max_repeated_step` 指标与行为规则管，TraceDiff 按 key 对齐天然容忍重复 |
| 7 | 首错定位的工程实现；两次 Trace 差异巨大（如 Prompt 完全重构）怎么办 | ◐ | D3、D4、D5、主题四 4.3.6、深答 15、16、S42 | 机制链路完整：复用已落盘 run summary → LCS 对齐 → 差异分类表 → 取第一处 → `no_visible_divergence` 兜底。**缺口：「几乎全变」的场景没写**。可组织口径：Prompt 重构不改 `module/action` 序列时对齐不受影响；连步骤序列都全变时 LCS 匹配极少，首错=第一个未匹配步骤，此时信息量低，报告会展示对齐统计（`alignment` / 匹配率）并交人工——这正是「首错是排障起点不是因果结论」的边界 |
| 8 | 适配契约如何抽象 Trace 核心要素 | ✅ | B2、深答 5、主题二速答 3 | `trace_id/final_output/events/fields/feedback/target_*/raw` 各字段职责逐条讲 |
| 9 | 不同框架 Trace 差异；最难兼容的 Case | ◐ | D6、S13、S14、深答 17、主题二速答 3 | 差异维度有（字段命名/嵌套、语义属性、事件模型）；**「最难兼容 case」未组织成故事**。真实素材：OTLP 的 `AnyValue` 属性数组（值全在 `{key, value:{stringValue}}` 里，需递归展开）、Phoenix 的 `traces` 包装层、AgentScope 的 typed events（不能直接吃 JSON，必须按事件类型映射）——挑一个讲透即可 |
| 10 | OTel 如何采集；离线导出数据清洗的坑 | ◐ | 10.7（平台自身 OTel span：run/case 父子、失败关闭）、D6、S13、十一 Q7（Micrometer vs OTel） | **这题有口径陷阱**：本平台对外的 Trace 接入是「离线导出文件解析」（normalized/openinference/openai 三格式），不是实时 OTLP receiver——面试官问「你们如何利用 OTel 采集」时，先分清两件事：平台自身执行链路发 span（10.7），外部 Agent 轨迹走导出文件（D6）。清洗坑：语义属性命名差异、`AnyValue` 嵌套、Phoenix 包装、用例缺失时硬失败不静默跳过 |
| 11 | 海量 Trace 数据膨胀；有没有采样机制 | ✗ | 仅 H2（换存储/上限/分页） | **缺口**。诚实口径：当前没有 Trace 采样机制——控制膨胀靠的是：结果批式落盘（32 条/批）、进程输出上限（1 MiB）、`TraceDiff` 300 步上限、报告不缓存完整 results（Dashboard 摘要缓存 512 个）；采样是被明确划出的边界（H1），演进方向是接入层流式处理 + 按需拉取。被问就承认边界再谈演进，不要现编采样实现 |

- **必背（技术核心，约占面试时间八成）**：Q4 四层评测、Q6/Q7 LCS 与首错、Q8 适配契约、Q12–Q14 队列与存储、Q15 回流防污染、Q17 挑战与 bug、Q19 产品对比。这些是「青铜 vs 王者」的真正分水岭，且每一题都有代码可翻。
- **准备到能聊（有素材、没组织）**：Q3 Java 17 新特性（record/switch 箭头已核实，虚拟线程没用）、Q9 最难兼容 Case、Q10 OTel 双角色（自身 span vs 离线导出）、Q11 采样边界、Q18 长上下文演进。

## 三、缺口与补法建议（按优先级）

1. **Q11 采样机制（唯一硬缺口）**：背下诚实口径——「当前无 Trace 采样；膨胀控制靠批式落盘 32 条/批、输出 1 MiB 上限、TraceDiff 300 步上限、报告摘要缓存；演进方向是接入层流式处理」。这本来就是 H1 承认的边界，答边界比编故事安全。
2. **Q3 Java 17 新特性**：可现场验证——`grep -rn "public record" assay-core/src/main --include="*.java" | wc -l`、`grep -rn "return switch" assay-core/src/main`。答 record（契约/配置/不可变模型，96 处）+ switch 箭头（操作符与聚合分发）+ 文本不用虚拟线程及理由。**别把「用了 Spring Boot」说成核心依赖**（enforcer 禁它进核心）。
3. **Q6 树状/图状 Trace**：记住三层降维——归一化时展开成线性 `events`、嵌套调用用连续块匹配、循环由 `max_repeated_step`/行为规则管；TraceDiff 只对齐线性序列，300 步上限防爆炸。
4. **Q7「Prompt 完全重构」**：首错=第一个未匹配步骤，信息量低时报告给出对齐统计交人工——正好呼应「排障起点，不是因果结论」的统一口径。
5. **Q9 最难兼容 Case**：从 OTLP `AnyValue` 递归展开 / Phoenix `traces` 包装 / AgentScope typed events 三选一，按 D6 + S13/S14 细节讲。
6. **Q1/Q16 个人经历类（实习生低优先级）**：文档按纪律不代编团队背景和业务数字；各备 2 句真实口径——Q1 用 A1 的痛点口径讲个人动因，Q16 用「个人项目 + 可复现实验替代业务数字」收尾。面试重心永远在技术实现题上。
