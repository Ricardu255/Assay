02

模块依赖分层图

箭头方向 = 依赖方向（上层依赖下层）。接口留在 assay-core，实现下沉到 store / runtime / extensions —— 这是整套架构最核心的一条边界。

编译依赖（上层 → 下层） 接口实现 / 打包聚合 旁挂、可选或 test 作用域
一句话概括依赖方向：所有模块都向下依赖 assay-core，而 assay-core 的 pom.xml 里只有 JUnit（test 作用域）—— 它不认识命令行、不认识存储实现、不认识 Spring，也不认识 LLM 客户端。扩展能力靠「接口在 core、实现在外」实现，app/pom.xml 的 enforcer 再从构建层面禁止 Spring / Micrometer / OTel 进入发行包。
03

按功能域拆解

这是「功能模块」视角：一个功能域可能横跨多个 Maven 模块，但接口与实现严格分开。先看九个域之间怎么串成一条链，再逐个域看它内部的流程；每个域都给出正式解释、大白话解释，以及它吃什么、吐什么、和谁打交道。

域间协作流程图 · 九个域如何串成一条链

读图要点：D5 不是主链上的一环，而是把「一次 run」包起来的调度壳 —— server 走 JobRunQueue → SuiteRunner，CLI worker 则重入 AssayCli.run("run", …)；D3 是 D2 内部的规则调用，不是独立的一段流程；D9 只从旁读取产物或提交任务，不参与判定。D8 到「下一轮」的橙虚线是人工接线：晋级账本与评测 store 分离，CaseLoader 只读显式传入的单个文件、不扫描目录，必须由人把 --output 路径指给下一轮的 --cases 或三集参数。

九个域逐项说明 · 每张卡片带一张域内流程图

D1 · 接入与归一化

适配层
正式解释

定义统一接入契约 ProjectAdapter，包含 Agent 调用、Trace 读取、硬门禁规则集、软质量规则集与最大并发五个能力；由 AdapterLoader 通过反射、JAR 内 META-INF/services 注册或 JSON 配置解析实现，把 Java 进程内、HTTP 进程外、离线导出文件、AgentScope typed events 四类异构来源映射为不可变的 NormalizedTrace，核心只消费该统一模型。

大白话

不管你的 Agent 是本地 Java 类、远端 HTTP 服务、还是别的框架导出的一个文件，先统一翻译成一张标准表格：这次的编号、最后说了什么、中间做了哪几步、每步属于哪个模块的哪个动作。翻译这件事全交给「转接头」，后面的评测程序只看这张表，不需要知道对面是谁。

D2 · 评测执行引擎

核心心脏
正式解释

EvaluationEngine.runSuite 负责一次运行的完整编排：获取运行锁、写入 run 元数据与用例清单哈希（resume 时校验身份与逐 case 内容哈希）、建立固定线程池与预算账本、按 maxInFlight 预投任务、逐 case 调用适配器并读取轨迹、执行四层规则、按最多 32 条批次写入 Results，最后 finishRun 并汇总 RunSummary。

大白话

就是「跑一遍」的总指挥：先占住这个运行目录不让别人写，再看哪些用例上次已经跑过可以跳过，然后开几个线程并发去调 Agent，边跑边记预算，攒够一小批就写一次盘，全跑完收尾出一份汇总。中途崩了，下次能从已有结果接着跑，不用从头来。

域内流程 · D2 评测执行引擎

易错口径：逐 case 内容哈希用于校验数据集是否被改动（改动即拒绝续跑），不参与「跳过哪些 case」的判断；批次大小 = min(32, maxInFlight)。

D3 · 四层规则与门禁

确定性判定
正式解释

Rules 以固定顺序执行 structure / behavior / consistency / feedback 四层检查，产出带 level（hard / soft / candidate）的 CheckResult；规则是声明式数据（10 种操作符、args 结构化子集匹配），不含脚本引擎。CaseResult.hardPass() 与 softWarningCount() 由 checks 派生重算。发布对比阶段另有一套独立的 CompareGate（block / warning / info），两者不可混用。

大白话

拿着标准表格逐条核对：该有的字段在不在、步数有没有超、同一个问题多跑几次结果一不一样、用户有没有给差评。核对结果分三档：硬失败（直接判不过）、软告警（记一笔）、候选（只当线索）。判定全是照着配置算出来的，没有随机数、不叫大模型，所以同一份输入结论唯一、能重放。

assay-core（rules / compare 包）
输入

输出
List<CheckResult> → CaseResult 的硬通过 / 软告警
关键类

被 EvaluationEngine.evaluateRules 与 CompareCommand 分别调用

D4 · 存储与崩溃恢复

双实现
正式解释

core 定义 Results 与 JobStore 两个接口；文件实现用目录 + JSONL 追加写、临时文件 ATOMIC_MOVE、一字节跨进程文件锁，并处理末行截断、缺换行、UTF-8 半字符三种尾部损坏（中间损坏报错）；JDBC 实现用 6 张表 + assay_job、SELECT … FOR UPDATE 与显式事务保证 claim 的原子性。Stores 工厂按 jdbc: 前缀选择后端。

大白话

两种记账方式：一种往文件里一行行追加，一种往数据库表里写。都要解决同一件事 —— 跑一半崩了怎么办。文件版允许把「最后没写完的那一行」砍掉重来，数据库版靠事务和行锁保证不会两个人同时领到同一个任务。上层完全不关心用的是哪种，换个前缀就切换。

D5 · 异步调度与队列

零中间件
正式解释

基于共享 JobStore 的持久化任务队列：claim 原子领取并授予租约，独立的单线程调度器按 lease/3 周期心跳续租，过期任务在 claim 前被回收；取消是协作式（写 cancel_requested + interrupt）；失败按 RetryPolicy.delayFor 指数退避写 next_attempt_at；幂等键由调用方提供，同键不同 payload 报冲突。语义是 at-least-once，不承诺 exactly-once。

大白话

不装 Redis、不装 Kafka，就用文件或数据库当任务清单。谁领了任务就先「占个座」，占座有有效期，干得久就每隔一小会儿喊一声「我还在」；要是真挂了，座位过期别人就能接手。重复提交用调用方给的一个钥匙防住 —— 同一个钥匙交两次，拿到的是同一个任务，内容不一样就直接报错而不是偷偷覆盖。

RunSpec / job payload、幂等键、max-attempts、lease 秒数
输出
任务状态机（QUEUED → RUNNING → SUCCEEDED / FAILED / CANCELLED）+ run-summary.json
关键类
JobRunQueueJobStoreRunSpecRunJobsSuiteRunnerRetryPolicyIdempotencyConflictException

D6 · 版本演化决策

准出判定
正式解释

EvolutionEngine 在 improvement / regression / holdout 三份数据集上分别跑基线与候选（三集缺一或为空则启动即失败），用 MetricStats 汇总指标、EvolutionComparison 计算用例四态迁移与逐集 delta；EvolutionPolicyEvaluator 依次执行 7 个 check（目标身份、回归、holdout、场景门禁、质量门禁、目标指标、改善证据），全部跑完累加三组理由、不短路；最后由 verdict 按固定优先级短路输出 accept / reject / rollback。若某集运行不完整，直接 rollback 并跳过 evaluator。

大白话

回答「新版本能不能发」。拿三组题分别给老版本和新版本做：想改好的那组、不能弄坏的老功能、还有一组憋着没给新版本看过的题。先看有没有弄坏老的（弄坏直接打回），再看有没有达标，最后要求必须拿得出「确实变好」的证据 —— 没变好也不算通过，得打回去继续改。所有判断理由都写下来，人能回头看为什么被拦。

D7 · 首错诊断与失败归并

辅助证据
正式解释

TraceDiff 用 module + action 签名构建步骤序列做 LCS 对齐（超 300 步降级为按位置比对），忽略时间戳与 span_id 等噪音字段，产出 first_divergence 与差异清单；Reporting.appendCaseTransitions 把发生回归的用例按 (role, category, module, action) 四元组归并成 Failure clusters，每簇给条数与前 5 个样例，按条数倒序。结果为可解释证据，不参与门禁决策。

大白话

版本退化时不重新跑一遍 Agent，直接把两次已经存下来的轨迹摊开对齐，找出「从哪一步开始不一样」——是少调了一步、参数变了、还是顺序挪了，都标出来。再把一堆失败按「哪套题 / 什么差异 / 哪个模块的哪个动作」归成几堆，人先去看最大的那堆。它只帮人缩小范围，不替人下结论，更不会自己说「根因是 X」。

first_divergence、divergences、Case transitions、Failure clusters 表

D8 · 人工复核与资产回流

数据飞轮
正式解释

三条入口链路对照

同一个评测引擎，三种「怎么被叫起来」的方式。这是最容易画错的一处：CLI worker 和 server worker 走的是两条不同的编排路径。

链路顺序编排归属租约 / 重试默认
A. 同步直连
assay run		 AssayCli.runSuite → Stores.open → engineFor → CaseLoader → EvaluationEngine.runSuite → Reporting.writeRunArtifacts assay-cli（无队列） 无租约；--retries 默认 0
B. CLI 队列
submit + worker		 submit → JobStore.submit → worker → claim → executeJob（起心跳）→ AssayCli.run("run", …) → 同 A → succeed / finish / fail assay-cli（QueueCommands） --lease-seconds 默认 30 → 心跳 10s；--max-attempts 默认 3
C. Server API
POST /api/runs		 RunController → RunService.start → JobRunQueue.submit → pollLoop / claim → RunJobs.spec → SuiteRunner.run → EvaluationEngine.runSuite → Reporting → writeSummary → jobs.succeed assay-server + assay-runtime job-lease-seconds 默认 60 → 心跳 20s；配置里 max-attempts 默认 1
为什么 B 不复用 C：CLI worker 的实现是直接重入 run 命令（QueueCommands.executeJob → AssayCli.run(runArgs(job))，重试次数 >1 时追加 --resume），因此它天然继承同步链路的全部行为；JobRunQueue + SuiteRunner 是 server 侧为了在 Spring 进程内起多线程 worker 而另写的一套编排。两者共享的是 JobStore 契约，不是执行代码。

边界与易混淆点

这些是画图时最容易凭印象画错、或把「设计」画成「已实现」的地方，逐条按源码标明。

八条必须说清的边界

  • 接口在 core，实现在外面。Stores、ResultStore、JdbcResultStore、AdapterLoader、OpenAiCompatibleReviewer、ReviewSamples、TestSelectionService、AutoEvolutionLoop、ScopeAudit 都不在 assay-core；core 里只有 Results / JobStore / EvaluationListener / LlmReviewer / ProjectAdapter 等契约与数据模型。
  • 两套 severity 不能混。四层评测是 hard / soft / candidate（写死在 CheckResult.level）；release 对比门禁是 CompareGate 的 block / warning / info，属于另一条命令链。
  • CLI 没有 queue 父命令。submit / worker / jobs / cancel / replay / prune / reindex-jobs 都是顶级命令；队列提交的 HTTP 入口是 POST /api/runs（server）或 POST /api/jobs（dashboard --worker）。
  • AgentProcessRunner / ContainerRunner 没有生产调用边。它们是提供给领域 AgentCaller 自行调用的工具类，main 源码里没有任何 adapter 调用它们；AutoEvolutionLoop 的沙箱是 TextArtifactWorkspace 文本制品目录，不是容器。容器默认参数确实是禁网 / 只读根 / drop ALL caps / 512m / 1 cpu / 128 pids。
  • 可观测 listener 不会自动创建。Micrometer / OTel 两个实现是库类，main 源码里没有实例化点；唯一注入缝是 spring-boot-starter 的 ObjectProvider<EvaluationListener>。CLI 与 SuiteRunner 生产路径硬编码 NOOP。
  • AgentScope 是转换库，不是适配器工厂。assay-agentscope 只提供 AgentScopeTraceAdapter.toTrace 与 AgentScopeEventRecorder，没有 ProjectAdapterFactory 实现；且因传递依赖冲突不进 assay.jar。
  • 退出码 2 不只来自用法错误。除 UsageException 外，select-tests 的 humanReviewRequired、audit-scope 的「非 no_obvious_issue / 非 clear_out_of_scope」也会返回 2；决策链本身只产 0（accept）/ 1（reject、rollback），不产生 2。
  • 四类接入都没有接生产上的真实框架。Java / HTTP / 离线文件是示例适配器 + 集成测试验证，AgentScope 有独立模块与 typed events 映射但未接真实应用；准确表述是「验证契约可实现」，不是「验证四个真实框架」。
关于发行包：app/target/assay.jar 只聚合 7 个模块（cli、examples、core、runtime、两个 store、dashboard），assay-server、assay-agentscope、三个 extensions 与 assay-integration-tests 都不在其中。Dockerfile 打的也是这个 CLI 发行版镜像，注释明确说明 Spring Boot server 是另一个 artifact。
